| D-023 | Cascade, agreement and misread safeguards | Adopted | Two RapidOCR views (full frame, pack crop) plus Tesseract on the crop; rotation retries only when no batch label was found; one bounded confirmation pass when exactly one reading has single-pass support; strict agreement unchanged (any disagreement is AMBIGUOUS); near-neighbour abstention unchanged (edit distance 2 for keys of 6+ characters); engine scores never used as evidence; `No alert found` shows the batch checked; model files hash-verified before loading |
| D-026 | Clean negatives need the user's confirmation | Approved by owner 2026-11-15; implemented | After a loosely cropped T003 was read as `HLA50019` by both OCR views (true `HLAS0019`) and gave `No alert found`. No clean negative (`No alert found` / `Expired`) is shown for any batch string, OCR-read or typed, until the user has compared it with the pack and ticked the confirmation; until then `Unable to verify` (`ocr_batch_unconfirmed` / `manual_entry_unconfirmed`). `Alert found` stays automatic. Confirmation means the printed number was checked, not that the medicine is genuine or safe. No automatic S/5 substitution; matching, thresholds and dataset unchanged. Rejected alternative: abstain on look-alike characters (94% of listed batches contain one) |
| D-025 | Review of V2 manual testing | Adopted | See `docs/V2_REVIEW.md`. Strict agreement kept (every looser policy accepted wrong batches in replay); rotation cascade not stopped early (would hide conflicts); ONNX threads bounded (`RAPIDOCR_INTRA_OP_THREADS`); Tesseract concurrent with RapidOCR (`TESSERACT_CONCURRENT`, measured -26%); engine warmed at app start; `MG` accepted as a dropped-F manufacturing label only when a month+year follow with no whitespace; look-alike-only conflicts explained, never resolved; manual-entry confirmation cleared when the number is edited; stale-server import error shows a restart instruction |
| D-027 | Alert-side check | Adopted 2026-11-15 (completion sprint; owner delegated technical decisions within the safety rules) | Every `Alert found` carries `Decision.action_check`: compare the printed batch character by character, and product, strength and manufacturer, with the listed record; the UI shows it under the alert with the batch read next to the listed batch; evidence names any listed batch within edit distance 2 (`matching.listed_neighbours`). Root cause: an alert rests on an exact listed batch plus product words, and a one-character misread of an unlisted sequential sibling would pass both (22 listed pairs within 2 edits, mostly one maker's sequences); manufacturer never blocks. Outcome, timing and thresholds unchanged. Rejected: abstaining when a listed neighbour exists (does not cover unlisted siblings, loses real alerts); delaying alerts (contradicts D-026). Post-demonstration: a conflicting-manufacturer rule and region-restricted product evidence, only with evidence |

## Approval protocol for OPEN items
Record owner, date, decision, rationale, affected docs and tests. Agents must not turn an OPEN item into an approved one.
